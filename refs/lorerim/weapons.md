# LoreRim weapon types worksheet

Reference for skills/weapons/design.md (Q-WPN-1, Q-WPN-2). The data part was generated by
`scripts/gen_lorerim_refs.py` from the research dump of 2026-11-11 (`weapon-types.tsv`, 13 140 WEAP
records). Fill in the **Sub-skill** column. Several keywords can map to the same sub-skill. You
don't need one sub-skill per weapon type.

**Reading the table**

- One row per *type keyword* (FormKey). The same EditorID can exist in several plugins as
  **different** keywords (e.g. `WeapTypeSpear` in `SkyrimSpearMechanic.esp` and in `NewArmoury.esp`).
  Rules must use FormKeys.
- *Animation type / skill* comes from the WEAP data: the engine animation class
  (`OneHandSword`, `TwoHandAxe`, …) and the skill the weapon trains. Modded types reuse vanilla
  animation classes. Halberds are `TwoHandAxe`, pikes are `TwoHandSword`, spears and javelins are
  `OneHandSword`. This makes the animation type a good **fallback** for unknown weapons.
- Many records carry **several** type keywords at once (bottom table): Greatsword + Pike,
  Mace + Whip, Sword + Katana… The classifier needs a priority order: the most specific one wins.
- Staves and wands (`WeapTypeStaff`, `WeapTypeWand`) are not melee weapons in this design. They
  feed `wands-staffs` (skills/enchanting/design.md, wands and staves). A wand has both keywords, so wand is checked first.
- Light/heavy bows and crossbows: Requiem keywords `REQ_WeaponType_BowLight/BowHeavy`,
  `REQ_WeaponType_CrossbowLight/CrossbowHeavy`. Crossbows also carry `WeapTypeBow`, so the
  animation type `Crossbow` or the REQ keyword decides.
- Records include NPC-only, test and unobtainable weapons. Counts are records, not frequency in
  play.

## Classifier: how the code could look

> **Decided (2026-11-11): keywords only, via KID.** The sub-skill list is in skills/weapons/design.md. The
> config is [`config/kid/SPO_WeaponClass_KID.ini`](../../config/kid/SPO_WeaponClass_KID.ini),
> generated by [`scripts/gen_kid_weapons.py`](../../scripts/gen_kid_weapons.py):
>
> - classes in priority order: casting (staves, wands: not weapons) → crossbows → bows →
>   archery-other → scythes → 2H polearms → 1H spears → quarterstaves → 2H sword / warhammer /
>   battleaxe → 2h-other → short sword → dagger → sword → war axe → mace → unarmed → 1h-other;
>   each class line excludes every class above it;
> - all source keywords by FormID; one line per (class, source plugin), so a missing plugin drops
>   only its own lines;
> - per-form fixes for NPC weapons whose type keyword is wrong (giant clubs with
>   `WeapTypeSword`, …);
> - `--check <dump>` simulates the rules on `weapon-types.tsv` (static keywords only).
>
> Static result: 13 081 of 13 140 records classified. The other 59 get a DLL fallback by hand
> (`1h-other` / `2h-other` / `archery-other`, design Q-WPN-11). The animation-based TOML classifier below is
> kept only as background.

> **Update (2026-11-11):** OCF already classifies modded weapons at runtime through KID, and KID
> 3.4 supports chained keywords and exclusions. The preferred variant is therefore our own
> `_KID.ini` that distributes `SPO_WeapClass_*` keywords from OCF, Requiem and vanilla keywords;
> the DLL then checks only those keywords. See [`../frameworks.md`](../frameworks.md) §2.3 and
> §4. The TOML-rule classifier below stays as the fallback, or as a source to generate the INI.
> The static counts in the Data section undercount OCF, because OCF keywords are added at
> runtime (R-19).

### Inputs available at runtime (CommonLibSSE-NG)

| Input | API (verify names) | Notes |
|---|---|---|
| Keywords | `weap->HasKeyword(kw)` / `BGSKeywordForm` | primary signal |
| Animation type | `weap->GetWeaponType()` → `RE::WEAPON_TYPE` (`kHandToHandMelee`, `kOneHandSword`, `kOneHandDagger`, `kOneHandAxe`, `kOneHandMace`, `kTwoHandSword`, `kTwoHandAxe`, `kBow`, `kStaff`, `kCrossbow`) | fallback; always present |
| Trained skill | `weap->weaponData.skill` | decides the parent main skill (1H / 2H / Archery) |

### Config (data, not code)

Rules reference keywords by **FormKey** (`Plugin.esp|0xLocalID`), never by EditorID. EditorIDs are
not loaded at runtime by default, and Requiem renames many of them. Rules are ordered, and the first
match wins:

```toml
# SKSE/Plugins/SkillPractice/weapons/00-base.toml   (more files can be dropped in: 10-newarmoury.toml …)
[[rule]]                       # per-form override, highest priority
form = "Skyrim.esm|0x0001F4"   # Unarmed
subskill = "unarmed"

[[rule]]
keyword = "Wand Keywords.esp|0x000800"     # WeapTypeWand
subskill = "wands-staffs"
[[rule]]
keyword = "Skyrim.esm|0x01E716"            # WeapTypeStaff
subskill = "wands-staffs"

[[rule]]
keyword = "NewArmoury.esp|0x0E457E"        # WeapTypePike (before WeapTypeGreatsword!)
subskill = "polearm"
[[rule]]
keyword = "Requiem.esp|0x9F9914"           # REQ_WeaponType_BowHeavy
subskill = "heavy-bow"
# …
[[rule]]
keyword = "Skyrim.esm|0x06D931"            # WeapTypeGreatsword
subskill = "greatsword"

[fallback]                                 # by animation type, if no keyword rule matched
OneHandSword = "sword"
OneHandDagger = "dagger"
OneHandAxe = "war-axe"
OneHandMace = "mace"
TwoHandSword = "greatsword"
TwoHandAxe = "battleaxe"       # also warhammers and halberds without keywords
Bow = "light-bow"
Crossbow = "light-crossbow"
Staff = "wands-staffs"
HandToHandMelee = "unarmed"
```

### Code sketch

```cpp
// Built once on SKSE::MessagingInterface::kDataLoaded.
struct WeaponRule {
    RE::FormID         formID   = 0;        // per-form override (0 = none)
    RE::BGSKeyword*    keyword  = nullptr;  // keyword rule
    SubSkillId         subSkill;            // index into the sub-skill registry
};

class WeaponClassifier {
public:
    void Load(const Config& cfg) {
        auto* dh = RE::TESDataHandler::GetSingleton();
        for (auto& r : cfg.weaponRules) {                     // keeps file + rule order
            WeaponRule rule{ .subSkill = registry.Id(r.subskill) };
            if (r.form)    rule.formID  = dh->LookupFormID(r.form->localID, r.form->plugin);
            if (r.keyword) rule.keyword = dh->LookupForm<RE::BGSKeyword>(r.keyword->localID, r.keyword->plugin);
            if (!rule.formID && !rule.keyword) { log::warn("unresolved weapon rule {}", r.text); continue; }
            rules_.push_back(rule);
        }
        for (auto& [anim, sub] : cfg.weaponFallback) fallback_[anim] = registry.Id(sub);
    }

    SubSkillId Classify(const RE::TESObjectWEAP* weap) {
        if (!weap) return fallback_[RE::WEAPON_TYPE::kHandToHandMelee];
        if (auto it = cache_.find(weap->GetFormID()); it != cache_.end()) return it->second;

        SubSkillId result = kNone;
        for (auto& r : rules_) {
            if ((r.formID && r.formID == weap->GetFormID()) ||
                (r.keyword && weap->HasKeyword(r.keyword))) { result = r.subSkill; break; }
        }
        if (result == kNone) {
            result = fallback_[weap->GetWeaponType()];
            log::debug("weapon {:08X} '{}' classified by animation type", weap->GetFormID(), weap->GetName());
        }
        cache_.emplace(weap->GetFormID(), result);
        return result;
    }
private:
    std::vector<WeaponRule> rules_;
    std::unordered_map<RE::WEAPON_TYPE, SubSkillId> fallback_;
    std::unordered_map<RE::FormID, SubSkillId> cache_;
};
```

- The parent main skill comes from the sub-skill registry. For safety it is checked against
  `weaponData.skill`, and a mismatch is logged. Example: a "spear" sub-skill under One-Handed used
  with a two-handed spear.
- The debug log lists every weapon that fell through to the animation fallback. Playing for a
  while then gives the list of keywords still missing from the config.

## Can sub-skills be created dynamically?

**Yes. Sub-skills are DLL data, not engine records**, so the set of sub-skills can come from
config files read at load time. Nothing is hard-coded:

- **Registry from config.** Each sub-skill is a config entry: string id, parent main skill, XP
  curve, decay, conversion `k/T/w`, cross-link class. A mod-specific file (e.g.
  `weapons/10-newarmoury.toml`) can add both new sub-skills **and** the keyword rules for them.
  This works like the drop-in config files of KID/SPID. Adding a weapon mod then means adding a
  config file, not changing code.
- **Co-save keyed by string id.** States are saved under the sub-skill id (`"polearm"`), not a
  numeric index. Adding a sub-skill later starts it at 0. A sub-skill that disappeared from the
  config is kept in the co-save, untouched, and logged, so removing a config file does not lose
  progress.
- **Cross-links follow automatically** from the parent class. A new 2H sub-skill gets the 1/2 link
  to other 2H sub-skills and 1/4 to 1H (design §6), without extra config.
- **Fully automatic creation** (an unknown type keyword produces a new sub-skill on the fly) is
  possible but **not recommended** as a default. Such a sub-skill has no perks and no tuned
  parameters. Its name would come from the EditorID, which is not available at runtime without
  extra mods. Every weapon mod with odd keywords would also clutter the UI. Better: fall back to
  the animation class, log the keyword, and let the user add a rule. An opt-in
  `autoCreateFromUnknownTypeKeywords = false` setting could exist for experiments.
- **Perks** for a config-defined sub-skill are still records in an ESP, or numeric bonuses
  computed in the DLL (design Q-DYN-9). With DLL-computed bonuses, a new sub-skill can also get a
  generic continuous effect without any ESP change.
