# Weapon class: KID keywords → weapon sub-skill

- **Status:** done (prototype implementation; runtime coverage pending).
- **Design:** [`skills/weapons/design.md`](../skills/weapons/design.md) (*Weapon class is
  determined by keywords only*, Q-WPN-2, Q-WPN-11); data:
  [`refs/lorerim/weapons.md`](../refs/lorerim/weapons.md); KID:
  [`refs/frameworks.md`](../refs/frameworks.md) §2.
- **Depends on:** *plugin-records* ([`plugin-foundation.md`](plugin-foundation.md): the
  `SPO_WeapClass_*` keyword records in our ESL).
- **Research:** R-19 (runtime coverage after KID), R-20 (OCF version, Animated Armoury); both are
  answered by the dump of this block.

## What it does

Gives every weapon exactly one `SPO_WeapClass_*` keyword (KID, data only) and maps it to a weapon
sub-skill in the DLL.

## Parts

1. **Keyword records.** One `KYWD` per class in `SkillPractice.esp` (ESL-flagged), EditorIDs
   exactly as used in [`config/kid/SPO_WeaponClass_KID.ini`](../config/kid/SPO_WeaponClass_KID.ini)
   (22 keywords: `grep -oE 'SPO_WeapClass_[A-Za-z0-9_]*[A-Za-z0-9]' … | sort -u`; the bare
   `SPO_WeapClass_` in a comment is not one). KID would create missing
   keywords itself, but we rely on real records (frameworks §2.1).
2. **KID INI.** Installed as `Data/SPO_WeaponClass_KID.ini`. Generated by
   [`scripts/gen_kid_weapons.py`](../scripts/gen_kid_weapons.py); do not edit by hand.
3. **DLL table** keyword → sub-skill, in the DLL source (it is fixed by the design):

   | Keyword | Sub-skill |
   |---|---|
   | `SPO_WeapClass_1H_Sword`, `…_1H_ShortSword`, `…_1H_Dagger`, `…_1H_Mace`, `…_1H_WarAxe`, `…_1H_Spear`, `…_1H_Scythe`, `…_1H_Unarmed`, `…_1H_Other` | `1h-sword`, `1h-short-sword`, `1h-dagger`, `1h-mace`, `1h-war-axe`, `1h-spear`, `1h-scythe`, `1h-unarmed`, `1h-other` |
   | `SPO_WeapClass_2H_*` | the matching `2h-*` |
   | `SPO_WeapClass_Archery_*` | `archery-*` (Archery is not managed in prototype 1: no XP) |
   | `SPO_WeapClass_Casting` | not a weapon: no weapon XP |

   Take the exact keyword names from the INI; if a name in the INI has no row here, that is a
   build-time error (unit test over the INI text).
4. **Lookup.** Keywords are found by EditorID among `BGSKeyword` forms of `SkillPractice.esp`
   (keywords keep their EditorID in memory), or by FormKey if the ESL is generated with fixed
   FormIDs (preferred: then look up with `TESDataHandler::LookupForm(localID, "SkillPractice.esp")`
   as §14 says).
5. **Cache** `TESObjectWEAP* → sub-skill`, filled lazily on first use, after KID has run (KID
   distributes in its own `kDataLoaded`; our lookups happen in game, so lazy is enough).
6. **Fallback** (Q-WPN-11): no class keyword → by hand / animation type: one-handed types →
   `1h-other`, two-handed → `2h-other`, bow / crossbow → `archery-other`, staff → not a weapon.
   Log `[class] fallback <weapon>` once per weapon.

## Debug

- The debug panel shows, for both hands, the equipped weapon, its class keyword and sub-skill.
- Button *Dump weapon classes*: logs every `TESObjectWEAP` in the data handler with its class
  keyword (or `fallback`) and plugin; summary counts per class. This is the runtime answer to R-19
  (compare with the static 13 081 / 13 140 in `refs/lorerim/weapons.md`).

## Prototype notes

- Fixed FormKeys 0x800–0x815 in SkillPractice.esp resolve at DataLoaded;
  `WeaponClasses.h` is checked against the KID file by the pure tests.
- Classification is cached lazily; multiple class keywords and fallbacks are
  logged. The runtime dump includes owner plugin, FormID, name and sub-skill.
- Beast races and crafting furniture exclusions use resolved vanilla FormKeys,
  never load-order-prefixed runtime IDs.

- Equip a vanilla sword, dagger, greatsword, warhammer, a LoreRim spear: the panel shows the
  expected class.
- Dump: no weapon has two `SPO_WeapClass_*` keywords; the count of fallbacks is small and
  listed.
