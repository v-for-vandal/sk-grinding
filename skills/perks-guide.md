# LoreRim perk worksheets: how to read

Generated by `scripts/gen_lorerim_refs.py` from the LoreRim research dump of 2026-11-11 (profile *Default*, `research-report.md`). Only perks that are nodes of a skill tree are listed (454 of 2 744 PERK records).

Every skill has its own files in `skills/<skill>/`: `perks.md` (the LoreRim tree), `perks-removed.md` (removed from the tree), `perks-ordinator.md` (Ordinator 9.31 perks not in LoreRim). Skills with a shared design keep them in the group folder with the skill as prefix: `weapons/one-handed.perks.md`, `armor/heavy-armor.perks-removed.md`, … Index: [`README.md`](README.md).

**How to read an entry**

- **Handle** (e.g. `1H-03`) — short name for notes; the real identifier is the **FormKey**
  (`localID:DefiningPlugin.esp`), plus EditorID. *Winner* = plugin whose override is active.
- **Origin** — *base game* = the record is defined in Skyrim.esm / Update / DLC. In LoreRim almost
  all of them are reworked (Requiem renames them `REQ_*`, Ordinator / Big Tweaks / Modern Combat
  Rework override them), so "base game" here means "the vanilla slot", not "vanilla behaviour".
  Whether a vanilla perk was *removed* from a tree cannot be seen from this dump (only tree nodes
  were exported).
- **Requires** — purchase conditions of the record (skill level, other perks, character level).
- **In game** — the description the player sees (`<br>` removed).
- **Records** — what the perk's effects actually do, rendered mechanically from the entry points
  and abilities: `weapon damage +20% — when OneHanded weapon` etc. Conditions on the item/spell
  are prefixed `item/spell:`, on the target `target:`. Scripted perks (quest/script effects)
  cannot be explained from records; they are marked *scripted*.
- **Proposal (auto)** — sub-skill this perk seems to belong to, guessed from keywords and text.
  Treat as a hint.
- **Sub-skill requirements** — for you to fill in: which sub-skill and level (current / floor /
  potential, see design Q-DYN-10) should be required to buy the perk; or "automatic perk of
  sub-skill X at level N" if it should leave the tree.

- **Ordinator 9.31 (not in LoreRim)** (per skill; from a dump of the *original*
  `Ordinator - Perks of Skyrim.esp`) — perks of Ordinator's own trees that are not nodes of the
  LoreRim tree. Handles `ORD-<skill>-NN`. *Type A* = Ordinator's own record, *type B* =
  Ordinator's version of a vanilla slot whose LoreRim winner is another mod (see the background
  section). The same original-esp versions also appear in the *Alternatives* of LoreRim entries
  as "Ordinator 9.31 (original esp, not loaded)". File: `perks-ordinator.md`.

- **Alternatives** (from the R-22 dump, `perk-override-chain.tsv`) — every other plugin's
  version of the same PERK record, in load order, from the master to the last loser. Versions
  identical to each other are merged (`A = B`); versions identical to the winner are listed in one
  line. *Differs from winner in* compares name, description, requirements, records, next rank and
  flags. Only the PERK record itself is versioned: abilities and spells inside *Records* are shown
  from their **winning** spell records, so an older version may describe a spell that a later mod
  changed (e.g. Requiem's *Penetrating Strikes* says +5% penetration, its ability shows the
  current 30).
- **Removed from the tree** (per skill) — perks that are nodes in some earlier version of the
  skill's AVIF tree but not in the final one, with the winning PERK version and its alternatives.
  File: `perks-removed.md`.


## Background: record identity, overrides, and bringing back Ordinator perks

### FormID, FormKey, EditorID

- In a plugin file every record has a 4-byte **FormID**. The high byte is the index of the master
  in *that file's* master list. The low bytes are the **local ID**.
- At runtime the engine replaces the high byte with the plugin's load-order index (`FE xxx` for
  ESL), so the runtime FormID of the same record differs between installations.
- **FormKey** (Mutagen term) = local ID + the plugin that *defines* the record, e.g.
  `079343:Skyrim.esm`. It does not depend on load order. SKSE configs write the same thing as
  `0x079343~Skyrim.esm` or `Skyrim.esm|0x079343`.
- **EditorID** is only a text label. Most record types do not keep it at runtime (keywords are an
  exception), and mods freely rename it.
- Perk links are always FormIDs, never names:
  - `HasPerk` in purchase conditions ("requires the previous perk");
  - **tree nodes** in the skill's AVIF record (perk FormID, grid position, child connections). The
    skills menu lets the player take a perk only if a connected parent node is owned and the
    perk's own conditions pass *(verify the exact rule)*;
  - **ranks**: a multi-rank perk is a chain of separate PERK records linked by *Next Perk*. A
    requirement must be added to **every rank record**, otherwise later ranks skip it.

### Overrides: the last plugin wins

- Mods change existing records by **overriding** them: they ship their own version of the record
  with the same FormKey. The engine loads only the version from the **last** plugin in load order
  (*winner* in the perk entries).
- Mods reuse vanilla perk FormIDs on purpose. Hundreds of other records point at them (recipes
  with `HasPerk SteelSmithing`, NPC perk lists, quests, scripts, other mods' conditions), and
  reworking a perk "in place" keeps all those links working.
- Example from One-Handed: of its 37 tree perks, **18 are defined in `Skyrim.esm`**. They are
  vanilla slots overridden in a chain: Requiem, then LoreRim - Weaponmaster, Modern Combat Rework,
  … `0BABE4:Skyrim.esm` is vanilla *Armsman*. Requiem renamed it `REQ_OneHanded_WeaponMastery1`
  and changed it, and the active version is from `LoreRim - Weaponmaster.esp`.
- New tree nodes are **new records** with the mod's own FormKey (`AD399A:Requiem.esp` Dagger
  Focus, Special Feats, Ordinator…). These can be overridden by later mods too.
- The tree itself is the AVIF record, and its winner decides the layout. For `AVOneHanded` the
  winner is `Ordinator - Perks of Skyrim.esp`, yet the tree contains mostly Requiem / vanilla-slot
  perks and only 4 Ordinator perks (Final Stand, Grand Slam, Execute, Death Adder). The suffix
  `_OrdASISExclude` most likely means "exclude from ASIS NPC perk distribution". It does not
  indicate how the perk got into the tree.

### Bringing back Ordinator's own perks without removing current ones

The full **Ordinator 9.31** is installed (plus *Optimised Scripts for Ordinator* and *OMEAR
Addition - Ordinator Perks*). The dump has 2 744 PERK records, of which 454 are tree nodes. So most
Ordinator perk records exist in the game but are not attached to any tree. There are two cases.

**Type A: Ordinator's own record** (FormKey in `Ordinator - Perks of Skyrim.esp`, e.g.
`222D59` Final Stand). The record, with its spells, scripts and conditions, is already loaded.
To bring it back:

1. Override the skill's AVIF record in our patch and add a **tree node** pointing at the perk
   (grid position, connection from a parent node).
2. Check the **winning** version of the perk record. LoreRim patches may have changed or disabled
   it (removed effects, impossible conditions).
3. Adjust the purchase conditions, which were written for Ordinator's own tree, and optionally add
   sub-skill requirements.

> **The Ordinator plugin in LoreRim is rebuilt.** The `Ordinator - Perks of Skyrim.esp` that LoreRim
> loads is not the file from the Ordinator 9.31 archive. Its masters include Requiem.esp,
> Requiem - Special Feats, NewArmoury.esp and Fury, it overrides **no** vanilla PERK record (all
> 38 Ordinator versions in the R-22 override chains are Ordinator's own records), and its AVIF
> overrides carry the LoreRim/Requiem trees. Which MO2 mod provides that file was not checked.
>
> The **original** esp (dumped separately) overrides 240 vanilla PERK records and has its own
> trees (19–39 perks per skill, of which only 4–13 are in the LoreRim trees). So type B exists, but
> only in the original file: those versions are not loaded at all. They are shown as
> "Ordinator 9.31 (original esp, not loaded)" in the *Alternatives* of LoreRim entries, and the
> Ordinator perks missing from LoreRim are in each skill's *Ordinator 9.31 (not in LoreRim)*
> section. A type B perk is brought back by copying it from the **original** esp.

**Type B: Ordinator's version of a vanilla slot** (Ordinator overrode `01234:Skyrim.esm`, a later
mod such as Weaponmaster overrode it again and won). Ordinator's version **does not exist at
runtime**, because only the winner is loaded. To bring it back as an additional perk:

1. Take the record version **from `Ordinator - Perks of Skyrim.esp` itself**, not the winner. xEdit
   shows every plugin's version side by side, and Mutagen can read one plugin on its own.
2. Copy it into our patch as a **new record** with a new FormID (xEdit: *Copy as new record
   into…*).
3. **Re-point self-references.** Ordinator perks are often "perk + ability/spell whose conditions
   check `HasPerk <this perk>`", plus scripts with properties pointing at the perk. In the copy
   these still point at `01234`, which now belongs to Weaponmaster. Every such reference must
   point at the new FormID, otherwise the effect silently does nothing. If the perk works through
   a quest, the quest may need copying too.
4. Copy the whole **rank chain** (*Next Perk*) and link the copies to each other.
5. Add a tree node as in type A.

The original `01234` stays with Weaponmaster, and everything else keeps pointing at it. No
current perk is removed.

**Practical notes**

- First extend the research dump: list all Ordinator PERK records with type (A/B), whether they
  are in a tree, whether the winner differs from Ordinator's version, and what they reference
  (spells, quests, scripts, self-`HasPerk`). That becomes a candidates worksheet to choose from.
- Build the patch as a separate plugin (e.g. `SkillPractice - Ordinator Return.esp`, ESL-flagged),
  generated by a **Mutagen script from a config** (perk, parent node, position) rather than by
  hand. AVIF records may change with LoreRim updates, and the script can then rebuild the patch
  and re-point self-references reliably. The CK perk-tree editor is handy for adjusting node
  positions but not for repeatable builds.
- The patch must load after every plugin that touches the AVIF records, otherwise the tree is
  overwritten.
- Check in game: tree layout (the constellation area is limited, and One-Handed is already
  dense), balance (Ordinator numbers target the vanilla damage model, not Requiem's), and
  scripts/quests.
- Adding tree nodes from the DLL at runtime (`ActorValueInfo::perkTree`) is possible in theory
  but means undocumented engine memory handling. The ESP route is standard.
